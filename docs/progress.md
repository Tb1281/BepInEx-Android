# Project Milestones & Architecture Decisions

This document specifies the engineering milestones, Architecture Decision Records (ADRs), and physical hardware verification history for the BepInEx Android port.

---

## 1. Architectural Decision Records (ADRs)

### ADR 1: Official Microsoft .NET Runtime Pack vs. Source Cross-Compilation
- **Context**: CoreCLR was originally cross-compiled from `dotnet/runtime` source via NDK, which required 1–2 hours per build, sudo host package installations, and risked mixing runtime-identifier (RID) BCL assemblies.
- **Decision**: Adopt Microsoft's official `Microsoft.NETCore.App.Runtime.android-arm64` NuGet package.
- **Outcome**: Deterministic download (<2 minutes), zero build-tool contamination, and guaranteed consistency between native CoreCLR and managed BCL assemblies.

### ADR 2: Selection of .NET 10 LTS over .NET 11
- **Context**: .NET 11 preview packs were evaluated, but MonoMod.Core strictly gated runtime versions and threw runtime exceptions under .NET 11.
- **Decision**: Pin the runtime to .NET 10 LTS (`10.0.12`).
- **Outcome**: Full compatibility with MonoMod, Harmony dynamic detours, and long-term support stability.

### ADR 3: Pure Java JNI Crypto PAL (No OpenSSL/BoringSSL)
- **Context**: Desktop CoreCLR relies on OpenSSL. On Android, bundling OpenSSL causes symbol collisions with system BoringSSL.
- **Decision**: Configure the official Android Crypto PAL (`libSystem.Security.Cryptography.Native.Android.so`), which delegates cryptographic primitives directly to Android's built-in Conscrypt and JNI providers.
- **Outcome**: Zero native OpenSSL dependencies; binary compatibility guaranteed across all Android OS versions.

### ADR 4: In-Process Hooking via `libfusion.so`
- **Context**: Desktop BepInEx relies on Doorstop launcher binaries. On Android, games launch under zygote/ART activity lifecycles.
- **Decision**: Implement `libmain.so` and `libfusion.so` to intercept `il2cpp_init` before the game engine initializes, directly hosting CoreCLR in-process.
- **Outcome**: Seamless lifecycle integration with standard Unity Android startup routines.

### ADR 5: Safe Dynamic Export Thunk Resolution
- **Context**: AArch64 dynamic linkers frequently export functions (such as `il2cpp_runtime_invoke`) via 4-byte jump stubs or literal-pool veneers (`LDR X16; BR X16`). Attaching inline hooks to small stubs corrupts function prologues.
- **Decision**: Implement `ExportThunkResolver` to follow branch displacement and validate target memory ranges via `/proc/self/maps` prior to hooking.
- **Outcome**: Prevents runtime crashes and `SIGILL` faults under modern Pointer Authentication (PAC) environments.

### ADR 6: Process Hosting Identity Shims
- **Context**: Running games inside an auxiliary launcher process (`com.bepinex.android:game`) causes identity conflicts with Firebase configuration lookups, component discovery, and Google Play Billing.
- **Decision**: Implement `GameResourceContext` (caller stack whitelisting & storage redirection), `FirebaseComponentDiscoveryFix` (manifest registrar supply), and `PlayBillingFix` (Pine method interception).
- **Outcome**: Full in-game playability on modern Unity 6000 games without unhandled exceptions or JNI overflows.

### ADR 7: Universal Thunk Resolution in `NativeDetour`
- **Context**: Injected hooks generated by `Il2CppInterop` (e.g. `MetadataCache::GetTypeInfoFromTypeDefinitionIndex`) passed 4-byte jump stubs directly to `NativeDetour`, causing Dobby to overwrite neighboring jump stubs in the table.
- **Decision**: Route all `NativeDetour` target pointers through `ExportThunkResolver.Resolve()`.
- **Outcome**: Guarantees that every native inline hook attaches to the true function body rather than a stub.

### ADR 8: AArch64 Inline Hook Space Guard
- **Context**: AArch64 inline hooks write 16 bytes (4 instructions). If an address has fewer than 16 bytes before a `RET` instruction (e.g., function epilogues), writing 16 bytes stomps into adjacent code.
- **Decision**: Implement `ExportThunkResolver.CanSafelyHook` to verify no `RET` instruction exists within the first 16 bytes. If violated, throw `InvalidOperationException` so `Hook.ApplyHook()` cleanly catches and skips the hook.
- **Outcome**: Prevents catastrophic native memory corruption (`SIGSEGV` in `mono_class_get_checked`).

### ADR 9: Android Native Logcat Decoupling
- **Context**: Unity outputs engine logs directly to Android Logcat (`Unity` tag), and BepInEx outputs to Logcat (`BepInEx` tag via `AndroidLogListener`). Setting `UnityLogListening = true` duplicates Unity messages and forces early `ClassInjector` initialization on boot.
- **Decision**: Set `UnityLogListening = false` as default in `BepInEx.cfg` and `IL2CPPChainloader.cs`.
- **Outcome**: Eliminates duplicate log traffic and avoids premature interop hook registration on vanilla launches.

### ADR 10: Il2CppInterop Hook Validation
- **Context**: `FindClassGetFieldDefaultValueXref()` in `Class_GetFieldDefaultValue_Hook.cs` traversed across tail-call branches into an epilogue (`0x1b5e81c`) on Unity 2022.3 ARM64.
- **Decision**: Validate that resolved hook candidates are non-null, aligned, and have at least 16 bytes before `RET`. Otherwise return `IntPtr.Zero`.
- **Outcome**: Matches Unity 6 fallback behavior and safely skips without generating invalid pointers.

### ADR 11: Il2CppInterop MetadataCache Hook Exclusion on Android
- **Context**: In upstream Il2CppInterop, `MetadataCache_GetTypeInfoFromTypeDefinitionIndex_Hook` used an `int index` delegate parameter. On Metadata v29+ (Unity 2022.3+), the function target `GetTypeInfoFromTypeHandle` takes a 64-bit struct pointer in `X0`. Forwarding through the hook truncated `X0` to 32 bits, zero-extending it to `0x502434c0` and triggering fatal `SIGSEGV (SEGV_MAPERR)`.
- **Decision**: Omit `GetTypeInfoFromTypeDefinitionIndexHook.ApplyHook()` from `InjectorHelpers.Setup()`, matching the legacy Android fork.
- **Outcome**: Custom MonoBehaviour types registered via `ClassInjector.RegisterTypeInIl2Cpp` load and initialize cleanly without crashing.

### ADR 12: BootstrapActivity Configuration Changes & State Preservation
- **Context**: Orientation and display topology changes during game bootstrap caused Android to recreate `BootstrapActivity`. Because `isGameLaunched` was set early in `onCreate`, the recreated instance falsely detected an already-launched game, scheduled an `AlarmManager` pending intent, and killed the process (`System.exit(0)`), which modern Android BAL then blocked.
- **Decision**: Add full `android:configChanges` to `BootstrapActivity` in `AndroidManifest.xml`, ignore `savedInstanceState != null`, set `isGameLaunched = true` only upon launching `StubActivity`, and preserve `SCREEN_ORIENTATION_UNSPECIFIED`.
- **Outcome**: Completely prevents premature process exits and BAL launch blocking on game startup.

### ADR 13: Release Minification, and the non-debuggable PAL blocker it exposed
- **Context**: The launcher shipped as `assembleDebug` and had never been built as a release APK. Turning on R8 revealed a blocker that debug-only development could not reach: **a non-debuggable build cannot start a game at all.**
- **Decision**: Keep `isMinifyEnabled`/`isShrinkResources` on for release — they are proven not to be the cause — and fix the `debuggable` blocker by initialising the crypto PAL through the Java class loader exactly once.
- **Outcome**: APK 104.4 MB → 53.4 MB (−49%); dex 57.6 MB → 7.9 MB. Cause of the dex bulk is `androidx.compose.material.icons.extended`, which ships 21,320 icon classes (4,264 × 5 variants) of which this app uses 33.

#### What was measured, and what was ruled out

Isolation was by building three configurations and booting each on device. `SM-S931N` / Android 17, *The Tower* 6000.3.15f1, `com.bepinex.android` 0.184:

| Build | `isMinifyEnabled` | `isDebuggable` | Result |
|---|---|---|---|
| debug | off | true | boots to `Chainloader startup complete` |
| release | on | false | SIGABRT |
| release | off | false | SIGABRT |

**R8 is not the cause.** The release APK's three PAL classes were dumped directly with `dexdump` and every one of the 17 descriptors in `provenance/pal-java-contract.txt` is present and unrenamed. Obfuscation is ruled out on evidence, not inference.

**The failure itself:**
```
GetClassGRef: class net/dot/android/crypto/DotnetProxyTrustManager was not found
Abort message: (same)
signal 6 (SIGABRT) ... com.bepinex.android:game
  #01 libSystem.Security.Cryptography.Native.Android.so
  #02 libfusion.so (dotnet_start_runtime()+1764)
```
The launcher, the Pine hooks, `findLibrary` redirection, the `il2cpp_init` hook and the CoreCLR host all reach this point normally. The abort happens inside the PAL's own `JNI_OnLoad`, with no managed frame to point at a cause.

**Why it went unnoticed**: every prior verification ran a debug build, where this works. Nothing about the visible behaviour differs — the launcher is fully functional, only the game launch dies.

#### The mechanism, and the fix

`init_platform_pal` (`fusion/src/dotnet.cpp`) `dlopen`s the PAL and calls `JNI_OnLoad` by hand, because CoreCLR is what loads it and Android never sees that dlopen. ART attributes a native library to a `ClassLoader` only when the Java loader loads it, so a dso arriving via bare `dlopen` has none and the PAL's `FindClass` falls back to the boot class loader — which cannot see `net/dot/android/crypto/*`.

That was the intermediate diagnosis. The initial fix attempted to call `System.load()` on the PAL from `BootstrapActivity` and skip native `JNI_OnLoad`. While this allowed *The Tower* to pass, it created two separate DSO instances due to Android linker namespace isolation (`clns-9` vs native namespace), leaving CoreCLR's copy with an uninitialized `g_vm` and crashing *Revolution Idle* during Cpp2IL SHA1 token computation.

This was subsequently replaced by the architectural solution in **ADR 15**: hooking `env->functions->FindClass` via VMT redirection during native `JNI_OnLoad`, completely eliminating `System.load()` and unifying PAL initialization into a single DSO instance.

Measured on device after ADR 15: the `GetClassGRef` abort and the Cpp2IL SHA1 `SIGSEGV` are both gone. Both *The Tower* and *Revolution Idle* reach active game playability.

The release blocker is resolved. What follows that line is a separate, pre-existing crash that affects debug and release alike and is not a release regression:

```
signal 11 (SIGSEGV), fault addr 0x8 ... UnityMain
  #00 firebase::database::Database::DeleteInternal()+192
  #01 firebase::database::Database::GetInstance(...)+792
  #02 Firebase_Database_CSharp_InternalFirebaseDatabase_GetInstanceInternal
```

Both builds die there, so it is not caused by minification, by `debuggable`, or by this fix. It is the game's own Firebase Realtime Database initialising in a hosted process. `FirebaseComponentDiscoveryFix` already rescues Firebase's component discovery and `FirebaseOptions`; the native `Database::GetInstance` failure is a different layer and remains open.

#### Two gaps this work found in the repository's own gates

1. **`verify_crypto_java.sh` inspected the wrong artifact.** The APK path was hardcoded to `apk/debug/app-debug.apk`, so the APK that ships was never checked. Now prefers `apk/release/app-release.apk` and names the file it inspected in its output.
2. **Its awk state machine could pass on the wrong class.** A single `inc` flag was set when a class descriptor matched and never cleared at the next class header, so one class's constructor could satisfy another class's check. That is fail-open, against operational principle 3.
3. **The stage that reads the dex never ran in CI.** `verify_crypto_java.sh` skips APK inspection when no APK exists, and `build-launcher-apk.yml` called it *before* Gradle. On a clean runner the dex stage was therefore permanently skipped — the gate reported PASS while the half it exists for was never examined. A second invocation now runs after the build.

### ADR 14: `proguardFiles` must be declared on every build type that can minify
- **Context**: `proguardFiles` was declared on `release` only. A debug build with `isMinifyEnabled` would therefore run R8 with **none** of `proguard-rules.pro` — and none of the keep rules in it, including the one protecting the PAL classes.
- **Decision**: Declare the same `proguardFiles` on `debug`.
- **Outcome**: `-keep class net.dot.android.crypto.** { *; }` is now enforced wherever minification can run. This was not hypothetical: enabling minify on debug stripped `DotnetX509KeyManager`'s constructor while the keep rule sat unread in the build file, and the only thing that noticed was `verify_crypto_java.sh` — pointed at the right artifact by luck, since it inspected debug while the failure was being investigated on debug.

### ADR 15: JNI FindClass VMT Redirection for Native-Hosted .NET Crypto PAL
- **Context**: In an initial fix attempt (ADR 13), `libSystem.Security.Cryptography.Native.Android.so` was preloaded via Java `System.load()` in `BootstrapActivity` to run `JNI_OnLoad` on a Java frame, skipping native `JNI_OnLoad`. While this passed *The Tower*, testing *Revolution Idle* caused a fatal `SIGSEGV` at `0x142f8` during Cpp2IL SHA1 token hashing. Android's dynamic linker namespace isolation created two distinct DSO instances: one in the Java ClassLoader namespace (`clns-9`) and another in the native namespace loaded by CoreCLR. The CoreCLR instance never ran `JNI_OnLoad`, leaving its internal `g_vm` null pointer uninitialized. Additionally, `System.load()` from private data directories triggers writable-ELF security warnings on Android 15+.
- **Decision**: Remove `System.load()` preloading from `BootstrapActivity`. Instead, capture the Application `PathClassLoader` as a JNI global reference during `fusion_bootstrap_from_libmain`, and temporarily redirect `env->functions->FindClass` via a custom VMT table during native `JNI_OnLoad` in `init_platform_pal()`. If the original `FindClass` returns null (due to lack of Java frames on `UnityMain`), fall back to `ClassLoader.loadClass()`.
- **Outcome**: A single DSO instance of the crypto PAL is loaded and fully initialized (`g_vm != nullptr`), cleanly resolving `net.dot.android.crypto.*` from any native thread without namespace fragmentation or duplicate DSO mappings. Validated on hardware with both *Revolution Idle* (complete Cpp2IL interop generation & SHA1 token calculation) and *The Tower*.

## 4. Verification & Testing Commands

To reproduce the verification test suite on a connected ADB device:

```bash
# 1. Verify logcat stream during boot
adb logcat -s fusion BepInEx Unity

# 2. Inspect intercepted Unity exceptions
adb logcat | grep -E '\[Error:Unity\]|\[Error:Il2CppInterop\]'

# 3. Pull generated BepInEx logs from device sandbox
adb pull /sdcard/Android/data/com.bepinex.android/files/BepInEx/LogOutput.log ./
```
